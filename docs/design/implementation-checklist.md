# Documentation implementation checklist

Working tracker for executing the [documentation architecture](documentation-architecture.md) according to the [implementation plan](implementation-plan.md). One section per phase; one entry per deliverable. Check an item only when its page verification steps pass and its blockers (if any) are closed.

**How to use this document**

- Before writing a page, read its **Sources** and verify every factual claim against them — never against legacy prose.
- Pages marked **gated** must not be written until the referenced blocker is dispositioned by a code owner.
- Cookbook/recipe pages follow the [example flow template](documentation-architecture.md#example-flow-template); hook pages follow the [hook-family page template](documentation-architecture.md#hook-family-page-template); all pages follow the [accessibility rules](documentation-architecture.md#accessibility-and-interpretability-rules) and end with a **Maintainer sources** section.
- Every full YAML example must pass `phaser validate`; bounded examples get an execution smoke test.

Outcome: Verified. `PoissonNoiseModel.calc_wave_update` raises `NotImplementedError()` at `phaser/engines/common/noise_models.py:112`; its `calc_loss` (lines 86-102) works fine. `AmplitudeNoiseModel`/`AnscombeNoiseModel` implement both `calc_loss` (29-45) and `calc_wave_update` (47-63). - [ ] B7 — **Code owner:** disposition ePIE position-correction TODO (`phaser/engines/conventional/solvers.py`). Gates position-refinement recipe for conventional engines. Outcome: Verified: the `# TODO: ePIE position update` comment at `phaser/engines/conventional/solvers.py:379` is stale — position correction for ePIE was added later (commit d0f9c20) and is functionally implemented: `epie_run` (`solvers.py:451,525-538`) computes a position-gradient step identical in form to LSQML's (`solvers.py:291-304`), and `EPIESolver.run_iteration` (363-414) applies it exactly as `LSQMLSolver.run_iteration` does. Requires code-owner disposition.
- [ ] B8 — **Code owner:** disposition suspected `max_step_size`/`step_size` assignment bug (`phaser/engines/common/position_correction.py`). Gates position-solver documentation. Outcome: Verified: confirmed bug. `SteepestDescentPositionSolver.__init__` (`phaser/engines/common/position_correction.py:14-16`) reads: `self.step_size = props.step_size` then `self.max_step_size = props.step_size` — both fields assigned from `props.step_size`; `props.max_step_size` (`SteepestDescentPositionSolverProps.max_step_size`, `phaser/hooks/solver.py:83`, default `None`) is never read, so the per-step cap is always `step_size` itself, never uncapped and never any user-specified larger cap.
